# KakaoReply 신뢰성 설계

문서 상태: **전체 제품 설계 명세 / M0·M1 합성 코드·검증 완료, 실제 연동 미검증**. 구현 증거와 미완료 범위는 [PROGRESS.md](PROGRESS.md)를 확인합니다.

이 문서는 KakaoReply의 자동 답장 기능이 어떤 조건에서 실행되고, 어떤 경우에 보류되며, 장애 이후 어떻게 복구되어야 하는지 정의합니다. 실제 구현과 Mac 검증 결과를 대신하지 않습니다. 필드명과 의미는 [CONTRACTS.md](CONTRACTS.md), [설정 예시](../examples/app-config.example.json), [스키마](../schemas/)를 기준으로 맞춥니다. 숫자와 정책은 초기 제품의 설계 선택이며, 상대의 감정이나 관계 상태를 예측하는 수치가 아닙니다.

## 1. 적용 범위와 기본 원칙

KakaoReply는 사용자가 지정한 1:1 카카오톡 대화에서 자신의 말투와 확인된 대화 맥락을 반영해 답장을 생성하는 Mac 앱입니다. 사용자 설정에 따라 자동 발송까지 지원합니다.

필수 원칙은 다음과 같습니다.

1. 자동 발송 대상은 사용자가 선택하고 검증한 채팅방 하나입니다.
2. 발송 여부, 대상, 작동 시간, 한도는 결정적인 애플리케이션 코드가 관리합니다.
3. LLM은 답장 제안과 제한된 액션만 반환하며, 수신자 선택이나 도구 실행 권한을 갖지 않습니다.
4. 사용자의 직접 답장이 확인되면 준비 중인 자동 답장을 취소합니다.
5. 새 메시지나 설정 변경으로 문맥이 달라지면 이전 문맥에서 생성한 답장을 사용하지 않습니다.
6. 결과가 불명확한 전송을 자동으로 다시 시도하지 않습니다.
7. 모든 자동 발송에는 엔진이 고정 안내 문구를 붙입니다.
8. 대화 내용은 검증되지 않은 입력 데이터입니다. 지침, 권한, 도구 설정으로 해석하지 않습니다.
9. 구현 완료, 시뮬레이터 검증 완료, 실제 Mac 검증 완료를 구분해서 보고합니다.

## 2. 보장하려는 범위와 보장하지 않는 범위

### 2.1 애플리케이션이 지켜야 할 불변조건

- 하나의 작업에 대한 자동 전송 시도는 최대 1회입니다.
- 한 시점에 카카오톡 UI를 조작하는 애플리케이션 작업은 하나입니다.
- 전송 직전의 검증을 통과하지 못한 결과는 전송하지 않습니다.
- 자동 모드가 꺼져 있거나 live_send_enabled가 false이면 실제 전송을 시작하지 않습니다.
- 대상이나 발신자를 확실히 식별하지 못하면 자동 전송을 보류합니다.
- Keychain 잠금 또는 암호화 키 접근 실패 시 민감정보 처리와 자동 발송을 중지합니다.
- LLM이 정책을 바꾸거나 비밀을 요구하는 내용을 반환해도 그 요구를 실행하지 않습니다.
- 처리한 이벤트, 작업 상태, 발송 시도에 관한 기록을 영속적으로 보존합니다.

### 2.2 표현하면 안 되는 보장

GUI 연동은 원격 시스템과 하나의 데이터베이스 트랜잭션으로 묶을 수 없습니다. 다음을 보장한다고 표현하지 않습니다.

- 카카오톡 서버에 정확히 한 번 전달된다는 보장
- 상대 기기에 수신되었다는 보장
- 상대가 읽었다는 보장
- UI 전송 직전과 실제 전송 사이에 사용자가 행동하는 경쟁 조건의 완전한 제거
- Mac의 모든 절전·잠금·앱 버전 조합에서의 무인 동작
- 설정한 응답 시간으로 상대의 서운함을 방지한다는 보장
- 말투가 비슷하면 실제 사용자의 생각이나 감정도 일치한다는 보장

CONFIRMED_LOCAL은 검증된 채팅방의 Mac 화면에서 현재 outbox 후보에 대응되는 새로운 outgoing UI echo를 확인했다는 뜻입니다. 도구의 성공 응답만으로 이 상태를 부여하지 않습니다. 원격 전달 완료나 상대 읽음 상태를 의미하지 않습니다.

## 3. 공통 설정 계약

시간 관련 flat 키의 단위는 초입니다. 코드, UI, 예제 설정, 테스트는 아래 이름과 기본값을 동일하게 사용합니다.

| 설정 | 기본값 | 의미 |
|---|---:|---|
| transport | mock | mock / kmsg_mcp / kmsg_cli |
| mode | off | off / draft / auto |
| live_send_enabled | false | 실제 카카오톡 전송 활성화 여부 |
| active_windows | [] | 비어 있으면 자동 발송 가능한 구간이 없음 |
| timezone | Asia/Seoul | 일정 계산 기준 IANA 시간대 |
| reply_delay | 600 | 최초 미응답 메시지부터의 기본 대기 |
| settle | 20 | 마지막 상대 메시지 후 묶음 처리 대기 |
| human_cooldown | 900 | 직접 답장 관측 후 사용자 우선 시간 |
| poll | 5 | 기본 관측 간격 |
| max_incoming_age | 1800 | 자동 답장 대상으로 인정할 최대 메시지 나이 |
| max_autoreplies_session | 3 | 세션당 자동 전송 시도 한도 |
| session_gap | 1800 | 새 대화 세션으로 구분할 무활동 간격 |
| max_per_hour | 6 | 최근 1시간 자동 전송 시도 한도 |
| max_per_day | 20 | 설정 시간대 기준 하루 자동 전송 시도 한도 |
| max_chars | 240 | 안내 문구를 포함한 최종 메시지 길이 상한 |
| llm_timeout | 30 | LLM 호출 1회의 제한 시간 |
| llm_retries | 1 | 최초 호출 이후 허용할 추가 호출 횟수 |

추가 보관 기본값:

- 원문 메시지 보관: 7일
- 최소한의 감사 메타데이터 보관: 30일
- 자동 응답 표시 방식: per_message
- 자동 응답 고정 접미사: **— 부재중 AI 답장**

설정값은 기본값과 별개로 스키마와 의미 검증을 거칩니다. 범위를 벗어난 시간·길이, 잘못된 시간대, start == end인 구간, reply_delay >= max_incoming_age처럼 응답이 불가능한 조합은 거절하고 기존 유효 설정을 유지합니다. 겹치는 유효한 작동 구간은 합집합으로 처리하며, 중첩 자체는 오류가 아닙니다. active_windows.days는 ISO 요일로 월요일 1부터 일요일 7까지 사용합니다.

### 3.1 모드와 실제 전송의 관계

| 모드 | 생성 | 실제 전송 |
|---|---|---|
| off | 자동 생성 없음. 명시적인 시뮬레이션 평가만 가능 | 없음 |
| draft | 설정된 정책에 따라 초안 생성 가능 | 없음 |
| auto | 정책을 통과한 답장 생성 가능 | live_send_enabled 및 나머지 모든 전송 조건 충족 시에만 가능 |

off 또는 draft로 전환할 때 live_send_enabled도 false로 갱신합니다. live_send_enabled=true는 kmsg_mcp 또는 kmsg_cli, auto 모드, 비어 있지 않은 active_windows, local 또는 external 공급자를 함께 요구합니다. mock에 live_send_enabled=true를 넣는 설정은 거절합니다.

live_send_enabled 하나만으로 전송되지 않습니다. mode, 대상 검증, 작동 시간, 한도, 현재 상태, 안내 문구, 키 접근, 문맥 버전 검증이 함께 필요합니다.

mock의 전송 상태 테스트는 합성 SimulatedDeliveryPort가 로컬 확인·오류·불명확 결과를 재현하는 도메인 시험으로 수행합니다. mock의 live_send_enabled는 false로 유지하며 외부 전송 adapter 호출은 0회여야 합니다. 이 시험을 위해 실제 SendGate를 우회하는 운영 옵션을 만들지 않습니다.

수동으로 샘플을 넣는 시뮬레이션과 실제 채팅방 감시는 분리합니다. 시뮬레이션 기능이 실제 전송 플래그를 우회하는 통로가 되어서는 안 됩니다.

## 4. 구성요소와 단일 실행 규칙

### 4.1 단일 DB actor 프로세스

실행 중인 KakaoReply 인스턴스에서 상태 변경을 담당하는 프로세스는 하나입니다. 이 프로세스가 다음을 소유합니다.

- 이벤트 정규화와 중복 관측 판정
- 대화별 epoch 변경
- 대기 작업과 생성 작업의 상태 전이
- 한도 예약과 전송 시도 기록
- 메모리·현재 상태의 버전 변경
- 감사 메타데이터 기록

같은 사용자 데이터 디렉터리를 두 인스턴스가 동시에 소유할 수 없도록 프로세스 잠금을 사용합니다. 잠금 충돌 시 두 번째 인스턴스는 관측·전송 worker를 시작하지 않고 명확한 상태를 반환합니다.

LLM 네트워크 호출처럼 오래 걸리는 처리는 DB 쓰기 트랜잭션 밖에서 실행합니다. 결과를 적용할 때 작업과 epoch를 다시 검증합니다.

### 4.2 전역 UI dispatcher

카카오톡 읽기, 대상 확인, 전송처럼 UI 상태에 영향을 줄 수 있는 동작은 전역 dispatcher를 통과합니다. 별도 HTTP handler나 LLM worker가 직접 kmsg를 호출하지 않습니다.

- 자동 관측은 기본적으로 poll 간격에 따라 dispatcher에 읽기 작업을 제출합니다.
- 전송 직전 대상 검증과 실제 전송은 같은 dispatcher 작업의 연속 단계로 처리합니다.
- 대기시간 계산과 LLM 호출 중에는 UI 실행권을 점유하지 않습니다.
- 장시간 실행되는 watch 사용을 선택하는 경우, 내부 UI 동작과 dispatcher의 직렬화가 충돌하지 않는지 증명해야 합니다. 증명 전에는 기본 polling 경로를 사용합니다.
- 애플리케이션 내부 직렬화는 사용자의 마우스·키보드 조작과 원격 휴대폰 발신까지 잠그지 않습니다.

### 4.3 transport 공통 인터페이스

mock, kmsg_mcp, kmsg_cli는 동일한 도메인 계약을 제공합니다.

- 상태와 기능 확인
- 대상 채팅방 바인딩 검증
- 최근 메시지 관측
- 전송 직전 대화 재조회
- 전송 요청과 로컬 결과 근거 반환

transport에서 제공하지 않는 원격 메시지 ID, 전달 확인, 읽음 상태를 만들어내지 않습니다. 모의 transport의 편리한 기능을 실제 transport도 갖는다고 가정하지 않습니다.

kmsg_cli를 구현할 때 프로세스는 인자 배열로 호출하고 shell 해석을 사용하지 않습니다. kmsg_mcp를 구현할 때 도구의 실제 이름, 입력 스키마, 확인 파라미터 의미를 현재 설치 버전에서 검증합니다. 원시 LLM 출력이 도구 호출 인자가 되는 경로를 만들지 않습니다.

## 5. 관측 이벤트와 식별 신뢰도

### 5.1 권장 정규화 정보

각 관측 이벤트에는 다음 정보가 필요합니다.

- event_id: 앱이 해당 발생에 부여한 로컬 ID이며 카카오 원본 ID가 아님
- binding_id: 확인한 대화의 앱 내부 ID
- observed_at: UTC 관측 시각
- source_time: 원본 시각이며 모르면 null
- source: mock / live_poll / live_watch / history_import
- sequence: 해당 관측 세션의 발생 순서
- origin: partner / owner / bot / system / unknown
- authorship: human_verified / bot_confirmed / unknown / not_applicable
- confidence.author: verified / ambiguous / system
- confidence.newness: verified / baseline / uncertain
- confidence.time: source / observation_only / missing
- text: 복호화된 메모리 안의 본문. 저장 시 민감 컬럼 암호화 적용
- 비교용 지문과 문맥 위치 정보는 엔진 envelope로 관리
- transport·파서 버전, 바인딩 버전, 관측 세션과 관측 공백 여부는 엔진 envelope로 별도 관리

message-event.schema.json은 복호화된 메모리 안의 이벤트 계약입니다. 실제 대화를 해당 JSON 그대로 로그·파일에 저장하지 않습니다. 엔진 envelope의 추가 필드를 additionalProperties=false인 이벤트 본문에 임의로 넣지 않습니다.

origin=owner는 본인 직접 발신이 확인된 경우, origin=bot는 outbox의 실제 발송에 대응되는 근거가 있는 경우에만 사용합니다. 본인 말투 자료에는 origin=owner와 authorship=human_verified를 모두 요구합니다. system/unknown 이벤트와 history_import·baseline은 신규 자동 답장 트리거가 아닙니다.

지문만 같다고 모든 메시지를 동일하게 취급하면 안 됩니다. 상대가 같은 문장을 실제로 두 번 보내는 경우와 UI가 동일 메시지를 반복 노출하는 경우를 문맥과 관측 순서로 구분해야 합니다.

### 5.2 신뢰할 수 없는 작성자

upstream 문서에는 작성자 식별이 안 되는 메시지가 특정 기본 표기로 표현될 수 있다고 안내되어 있습니다. 특정 문자열만 보고 사람의 발신이라고 단정하는 구현은 허용하지 않습니다. 자세한 도구 동작은 이 문서 마지막의 upstream 근거와 설치 버전에서 확인합니다.

식별이 불명확한 이벤트의 origin은 unknown으로 유지합니다. unknown 이벤트가 현재 대화의 답장 필요 여부에 영향을 줄 수 있으면 관련 자동 답장 작업을 보류합니다.

### 5.3 초기 기준과 관측 공백

앱 최초 실행, 재연결, Mac 절전 복귀, 채팅방 재바인딩 이후에는 기준 대화를 다시 구성합니다.

- 기준 대화의 기존 메시지로 신규 자동 답장을 만들지 않습니다.
- 관측된 시각을 원래 발신 시각처럼 표시하지 않습니다.
- 연속 관측의 짧고 검증된 스냅샷 차이로 신규 발생을 확인했으면 source_time=null, confidence.time=observation_only를 유지한 채 observed_at을 대기 기준으로 사용할 수 있습니다. 초기 기준, 관측 공백, history_import에는 이 예외를 적용하지 않습니다.
- 관측 공백 동안 도착한 메시지의 신선도를 확인할 수 없으면 자동 답장 대상으로 승격하지 않습니다.
- 이전에 저장한 유효한 대기 작업도 현재 상태와 메시지 나이를 다시 검증합니다.

## 6. 대화 epoch와 작업 생명주기

### 6.1 epoch 정의

대화마다 단조 증가하는 epoch를 저장합니다. 답장 의사결정에 영향을 주는 검증된 변화가 있을 때 증가시킵니다.

- 새 상대 메시지
- 사용자 직접 발신
- 대상 바인딩 변경
- mode, live_send_enabled, 작동 시간, 한도 등 관련 설정 변경
- 현재 상태와 사용 가능한 사실의 변경·만료
- 중지 또는 재개에 따른 실행 상태 변경

중복 관측으로 판정된 이벤트는 epoch를 올리지 않습니다. 이벤트 식별을 확신할 수 없으면 새 이벤트라고 무조건 간주하는 대신 해당 채팅방을 보류합니다.

각 생성 작업은 생성 시작 당시의 epoch, 정책 버전, 말투 프로필 버전, 사용한 fact 버전을 저장합니다. READY 상태 진입과 DISPATCHING 상태 진입 모두 현재 값과 비교합니다.

### 6.2 상태 정의

| 상태 | 의미 | 실제 전송 가능 여부 |
|---|---|---|
| PENDING | 응답 조건을 기다리는 작업 | 불가 |
| GENERATING | 특정 문맥 버전으로 모델 호출 중 | 불가 |
| READY | 형식과 정책 검증을 통과한 결과 보유 | 최종 검증 이후에만 가능 |
| DISPATCHING | 전송 의도와 시도를 영속 저장하고 UI 전송 단계에 진입 | 현재 작업의 단일 시도만 |
| CONFIRMED_LOCAL | 정의된 로컬 확인 근거가 충족됨 | 추가 시도 없음 |
| CANCELED_HUMAN | 사용자의 직접 발신으로 취소 | 없음 |
| CANCELED_STALE | 문맥 또는 설정 변경으로 결과가 오래되어 취소 | 없음 |
| SKIPPED_POLICY | 시간·한도·정보 부족·식별 문제 등 정책상 보류 또는 제외 | 없음 |
| FAILED_BEFORE_DISPATCH | 실제 전송 시도 전 확정된 실패 | 같은 작업 자동 발송 없음 |
| DELIVERY_UNKNOWN | 전송 시도 이후 실제 결과가 불명확함 | 자동 재시도 없음 |

### 6.3 허용 전이

| 현재 상태 | 허용되는 다음 상태 |
|---|---|
| PENDING | GENERATING, CANCELED_HUMAN, CANCELED_STALE, SKIPPED_POLICY, FAILED_BEFORE_DISPATCH |
| GENERATING | READY, CANCELED_HUMAN, CANCELED_STALE, SKIPPED_POLICY, FAILED_BEFORE_DISPATCH |
| READY | DISPATCHING, CANCELED_HUMAN, CANCELED_STALE, SKIPPED_POLICY, FAILED_BEFORE_DISPATCH |
| DISPATCHING | CONFIRMED_LOCAL, DELIVERY_UNKNOWN |
| 나머지 종료 상태 | 같은 작업에서 다른 상태로 되돌리지 않음 |

새로운 정당한 입력 때문에 재평가가 필요한 경우 기존 작업을 되살리지 않고 새로운 작업을 생성합니다. DELIVERY_UNKNOWN을 해결하기 위해 동일 답장을 자동으로 새 작업에 복제하는 방식도 금지합니다.

### 6.4 상태 기록의 일관성

전송 시도 횟수와 한도 예약은 DISPATCHING 전이와 같은 DB 트랜잭션에서 기록합니다. 작업별 자동 전송 시도 횟수는 1을 넘을 수 없습니다.

DISPATCHING 저장 이후 프로세스가 죽으면 실제 UI 호출 전인지 후인지 확실히 알 수 없을 수 있습니다. 이 경우 재시작 후 DELIVERY_UNKNOWN으로 복구하고 자동 재시도하지 않습니다.

## 7. 응답 시간 정책

### 7.1 최초 미응답과 연속 메시지

미응답 묶음에는 다음 시각을 별도로 저장합니다.

- first_unanswered_at: 묶음에서 처음 관측·검증한 미응답 상대 메시지 시각
- last_partner_at: 묶음에서 마지막으로 검증한 상대 메시지 시각
- human_cooldown_until: 사용자 우선 상태의 종료 시각

응답 가능 시각은 다음 세 값 중 가장 늦은 시각을 기준으로 합니다.

1. first_unanswered_at + reply_delay
2. last_partner_at + settle
3. human_cooldown_until

추가 메시지는 문맥과 last_partner_at을 갱신하지만 first_unanswered_at을 무조건 덮어쓰지 않습니다. settle이 지나기 전에 상대가 계속 메시지를 보내면 성급하게 중간 답장을 보내지 않습니다. 작업이 max_incoming_age 범위를 벗어나면 무기한 대기하지 않고 정책상 제외합니다.

### 7.2 직접 답장 우선

사용자 직접 발신을 신뢰할 수 있게 관측하면:

1. 현재 epoch를 증가시킵니다.
2. 관련 PENDING, GENERATING, READY 작업을 CANCELED_HUMAN으로 종료합니다.
3. 직접 발신 이전의 미응답 묶음을 종료합니다.
4. human_cooldown_until을 갱신합니다.
5. 이후 새 상대 메시지는 새 묶음으로 처리하되 cooldown을 함께 적용합니다.

봇이 보낸 문장의 UI 재관측을 사용자 직접 답장으로 오인하면 안 됩니다. 반대로 봇 전송 기록과 작성자 판정이 모호하면 사람의 행동을 추정하지 않고 보류합니다.

### 7.3 작동 구간과 날짜

- 모든 저장 시각은 UTC 기준으로 기록하고 일정 판단에 timezone을 적용합니다.
- 구간은 시작 포함·종료 미포함으로 정의합니다.
- 중첩 구간은 합집합으로 처리하고 그 때문에 작업이나 한도 카운터를 복제하지 않습니다.
- active_windows.days는 ISO 요일을 사용하고 start == end인 구간은 거절합니다.
- 자정을 넘는 구간은 시작 요일의 구간으로 정의합니다.
- active_windows가 비어 있으면 자동 발송하지 않습니다.
- 전송 시각이 작동 구간 밖으로 넘어가면 SKIPPED_POLICY로 종료합니다.
- 다음 작동 구간 시작 시 오래된 보류 메시지를 일괄 전송하지 않습니다.
- DST 시간대를 지원하면 존재하지 않거나 중복되는 현지 시각의 처리 정책을 별도 명세·테스트합니다. 미지원 시간대는 설정에서 명시적으로 거절합니다.

### 7.4 시스템 시각 변경

동일 실행 세션에서 짧은 대기는 가능한 경우 monotonic 시계를 사용합니다. 영속 재시작 복구에는 UTC 시각과 신선도 검증을 사용합니다. 시스템 시각이 크게 바뀌었음을 감지하면 기존 타이머를 그대로 발화시키지 않고 스케줄을 재평가합니다.

## 8. 응답 한도와 세션

대화 세션은 검증된 대화 활동 사이에 session_gap 이상의 무활동 간격이 있으면 새로 시작합니다. 사람이 직접 답했다고 세션 카운터를 무조건 0으로 만들지 않습니다.

기본 한도는 세션 3회, 최근 1시간 6회, 현지 날짜 하루 20회입니다. UI에는 세 값의 차이를 설명합니다.

한도는 DISPATCHING 진입 시 예약합니다. DELIVERY_UNKNOWN도 실제로 보내졌을 수 있으므로 한도 사용으로 유지합니다. 한도 계산에서 불명확한 전송을 제외해 반복 시도를 허용하면 안 됩니다.

한도에 도달하면 해당 작업은 SKIPPED_POLICY가 됩니다. 다음 창이나 다음 날짜에 같은 작업이 저절로 살아나지 않습니다.

## 9. LLM 출력과 사실 검증

### 9.1 출력 계약

LLM 출력은 다음 네 필드만 갖는 JSON 객체입니다.

| 필드 | 허용 의미 |
|---|---|
| action | reply / hold / notify_owner / no_reply |
| reply_text | 답장 본문. 실제 발송 제어 명령이 아님 |
| reason_codes | reply-decision.schema.json의 enum 중 중복 없는 1~4개 코드 |
| used_fact_ids | 현재 요청에 제공된 유효 사실의 부분집합. 중복 없이 최대 20개 |

수신자, 도구 호출, 파일 경로, 실행 명령, API 키, 설정 변경을 위한 필드는 허용하지 않습니다. 알 수 없는 필드, 잘못된 액션, 제공되지 않은 fact ID는 검증 오류입니다.

reply의 reply_text는 비어 있으면 안 됩니다. hold와 no_reply는 reply_text가 빈 문자열이어야 합니다. notify_owner는 로컬 알림이며, 본문이 있으면 사용자에게 보여줄 초안으로만 사용합니다. reply가 아닌 액션은 상대에게 전송하지 않습니다. draft 모드에서 action=reply가 나와도 실제 전송하지 않습니다. reply 액션도 다른 정책 조건을 모두 통과해야 합니다.

reply_text의 스키마 상한은 1,000 코드 포인트입니다. 실제 발송에는 접미사와 줄바꿈까지 포함한 최종 텍스트의 max_chars를 별도로 적용합니다.

이유 코드의 허용 목록은 다음과 같으며 코드 추가·변경 시 스키마와 UI·fixture를 함께 갱신합니다.

- ROUTINE_REPLY
- ACKNOWLEDGEMENT
- MISSING_FACT
- CONFLICTING_FACTS
- EXPIRED_FACT
- COMMITMENT_REQUEST
- RELATIONSHIP_DECISION
- MONEY_REQUEST
- URGENT_OWNER_ATTENTION
- UNSUPPORTED_CONTENT
- UNTRUSTED_INSTRUCTION
- NO_REPLY_NEEDED
- INVALID_CONTEXT

이유 코드는 짧은 제품 상태 코드이며 비공개 사고 과정이나 관계·감정 점수가 아닙니다. 수신자, epoch, 설정 revision, 프로필 버전은 모델 출력에 추가하지 않고 엔진 envelope로 관리합니다.

### 9.2 말투와 사실

- 말투 예시는 인간이 직접 작성한 것으로 확인된 메시지 또는 사용자가 명시적으로 선택한 자료에서만 가져옵니다.
- 봇이 자동 발송한 문장과 생성만 된 문장은 본인의 새로운 말투 표본으로 수집하지 않습니다.
- 수정 피드백은 문체 교정과 사실 변경을 구분해서 저장합니다.
- 현재 상태는 유효시간과 사용자 확인 여부를 갖습니다.
- 기억에는 출처, 생성 시각, 확인 상태, 수정·철회 상태를 기록합니다.
- 대화에서 추출한 후보 기억은 자동으로 확정 사실이 되지 않습니다.
- 위치, 식사 여부, 약속 확정처럼 확인되지 않은 사실을 본인 상황인 것처럼 단정해서 보내지 않습니다.

### 9.3 생성 제한

각 LLM 호출 제한 시간은 llm_timeout입니다. 최초 호출 이후 추가 호출은 llm_retries만큼만 허용합니다. 잘못된 JSON을 고치기 위한 호출도 재시도 예산에 포함합니다.

문맥 변경으로 취소된 결과를 뒤늦게 적용하지 않습니다. 취소 신호를 모델 공급자가 지원하지 않더라도 애플리케이션은 결과를 폐기할 수 있어야 합니다.

## 10. 자동 응답 표시와 길이

자동 전송의 최종 메시지는 검증된 reply_text에 엔진이 다음 접미사를 붙여 구성합니다.

**— 부재중 AI 답장**

- v1 표시 방식은 per_message로 고정합니다.
- 이 접미사는 모델이 생성하거나 생략하도록 맡기지 않습니다.
- 일반 설정이나 프롬프트로 비활성화할 수 없습니다.
- 코드 자체의 표시 정책을 바꾸는 제품 변경은 이 명세의 일반 설정 범위 밖입니다.
- max_chars는 본문, 연결 줄바꿈, 접미사를 포함한 최종 텍스트에 적용합니다.
- 최종 텍스트를 NFC 정규화한 뒤 Unicode code point 수를 계산합니다. UI도 같은 규칙을 사용하며 JavaScript의 UTF-16 string.length를 그대로 길이 기준으로 쓰지 않습니다. 결합 문자와 이모지 사례를 검증합니다.
- 상한을 넘으면 의미를 자르거나 표시 문구를 지우지 않습니다. 허용된 재생성 예산 내에서 줄이거나 보류합니다.

## 11. 전송 절차와 불명확 결과

전송 코드는 다음 순서를 지킵니다.

1. 작업이 READY인지 확인합니다.
2. mode, live_send_enabled, 대상 바인딩, 작동 시간, 한도, 키 상태를 확인합니다.
3. 전역 UI dispatcher를 통해 최신 대화와 대상을 재검증합니다.
4. 직접 답장, 새 메시지, epoch와 사실 버전 변경을 확인합니다.
5. 최종 본문과 고정 접미사를 검증합니다.
6. DB 트랜잭션으로 작업 소유권을 확보하고 DISPATCHING과 단일 시도 의도를 기록합니다.
7. 동일 dispatcher 작업에서 실제 전송을 최대 1회 요청합니다.
8. 도구가 제공한 근거를 해석해 CONFIRMED_LOCAL 또는 DELIVERY_UNKNOWN으로 기록합니다.

도구의 성공 반환만으로 CONFIRMED_LOCAL을 부여하지 않습니다. 검증된 채팅방에서 현재 outbox 후보에 대응되는 새로운 outgoing UI echo가 필요합니다. 같은 문구가 과거에 존재했다는 사실만으로 확인하지 않습니다. 새 발생·본문·대상·관측 순서를 대응시키는 기준은 adapter 계약과 실제 Mac 검증으로 정합니다. echo가 없거나 일치 근거가 불충분하면 DELIVERY_UNKNOWN으로 남깁니다. mock 테스트는 같은 로컬 관측 근거를 합성으로 재현합니다.

### 11.1 결과별 처리

| 상황 | 처리 |
|---|---|
| 모델·형식·정책 검증에서 확정 실패 | FAILED_BEFORE_DISPATCH 또는 SKIPPED_POLICY |
| 실제 전송을 시작하기 전 확정된 프로세스 준비 실패 | FAILED_BEFORE_DISPATCH |
| DISPATCHING 기록 이후 프로세스 종료 | DELIVERY_UNKNOWN |
| 실제 전송 요청 이후 시간 초과 | DELIVERY_UNKNOWN |
| 전송 뒤 확인 대상이나 창이 모호함 | DELIVERY_UNKNOWN |
| 검증된 방에서 현재 후보와 대응하는 새로운 outgoing UI echo 확인 | CONFIRMED_LOCAL |

DELIVERY_UNKNOWN이 있으면 해당 채팅방의 새로운 자동 전송도 보류하고 사용자에게 상태를 보여줍니다. 사용자가 실제 대화를 확인한 뒤 미발송이라고 판단하더라도 기존 작업을 자동 재시도하지 않습니다. 별도의 명시적인 재작성·발송 동작으로 처리하고 원래 불명확 이력을 보존합니다.

### 11.2 성공한 답장이 해결한 수신 범위

각 답장 후보는 생성에 사용한 미응답 inbound 이벤트 범위를 불변 스냅샷으로 보유합니다. CONFIRMED_LOCAL이 되면 이 후보의 문맥에 포함되어 실제로 처리한 범위만 해결 상태로 표시합니다.

- 확인된 범위에 해당하는 first_unanswered_at과 pending 묶음만 정리합니다.
- 후보 생성 이후나 발송·확인 중 도착한 새로운 상대 메시지를 함께 해결한 것으로 취급하지 않습니다.
- 새 상대 메시지가 남아 있으면 그 새 묶음의 최초 미응답 시각부터 fresh reply_delay를 적용하고 last_partner_at과 settle도 새 범위로 계산합니다.
- 다른 후보에 속한 이벤트나 현재 최신 대화 전체를 일괄 해결하지 않습니다.
- 자기 발신 UI echo는 outbox 근거를 통해 origin=bot으로 분류합니다.
- 봇의 발신은 human_cooldown을 시작하거나 연장하지 않습니다.
- 봇의 발신은 세션 자동응답 횟수나 시간·하루 한도를 초기화하지 않습니다.
- DELIVERY_UNKNOWN에서는 어떤 범위가 실제로 답장을 받았는지 확정하지 않으며, 원래 불명확 작업과 관련 이벤트를 보존합니다.

이 처리는 이벤트 범위와 작업 상태를 확인하는 DB actor의 한 트랜잭션으로 적용합니다. 전체 대화의 최신 시각만 보고 미응답을 지우는 구현은 금지합니다.

## 12. 개인정보와 인증정보

### 12.1 민감 저장

대화 원문, 생성문, 기억 내용, 채팅방명 등 SQLite의 민감 컬럼에는 AEAD 암호화를 적용합니다. 암호화 키는 Mac Keychain에 보관합니다.

- 키 접근 실패 시 평문 컬럼, 환경변수, 설정 파일, 임시 파일로 우회하지 않습니다.
- 암호화 실패는 저장 실패이며, 성공으로 처리하지 않습니다.
- 암호화 nonce와 연관 데이터 구성은 검토된 라이브러리를 사용합니다.
- 필요한 비민감 인덱스·식별 메타데이터는 별도로 설계하되 원문을 로그에 복제하지 않습니다.
- Linux mock 검증에서는 합성 데이터만 사용하고 ephemeral key만 허용합니다.
- 실제 개인 대화를 Linux mock 환경으로 옮겨 테스트하지 않습니다.

KakaoReply의 Keychain 보장과 kmsg가 자체적으로 관리하는 카카오톡 인증정보의 보관 방식은 다릅니다. KakaoReply가 kmsg의 자체 인증 보관까지 Keychain으로 보호한다고 설명하지 않습니다. upstream의 현재 동작을 별도로 검토하고 설정 화면과 운영 문서에 구분해서 적습니다.

### 12.2 모델 공급자와 외부 전송

사용자가 선택한 모델 공급자와 전송 데이터 범위를 설정 화면에 표시합니다. 로컬 모델 선택과 외부 API 선택을 동일한 개인정보 경로라고 설명하지 않습니다.

LLM API 키는 프런트엔드 번들, 브라우저 저장소, 일반 설정 응답, 로그에 포함하지 않습니다. 인증 오류를 디버깅하기 위해 토큰을 출력하지 않습니다.

### 12.3 보관과 삭제

- 원문은 기본 7일, 감사 메타데이터는 기본 30일 보관합니다.
- 원문 삭제 시 그 원문에서 파생된 기억·요약·검색 데이터의 잔존 여부도 함께 처리합니다.
- 사용자가 별도로 선택해 보관하는 말투 예시는 보관 범위와 삭제 기능을 명확히 구분해야 합니다.
- 사용자의 전체 삭제 요청에는 파생 데이터와 저장된 생성문을 포함합니다.
- 백업을 제공한다면 암호화, 삭제 대상, 복원 시 삭제 이력 적용 정책을 함께 정의합니다.
- SQLite 파일·WAL·백업·운영체제 스냅샷까지 물리적으로 완전 삭제된다고 보장하지 않습니다.
- 감사 메타데이터에는 이유 코드와 처리 결과를 우선 기록하고 원문을 기본 포함하지 않습니다.

## 13. 로컬 관리 API와 입력 경계

로컬 웹 UI의 서버는 루프백에 바인딩합니다. 여기에 더해 명시적인 origin 검증, CSRF 방어, 사용자 세션 또는 로컬 토큰 검증을 적용합니다.

- 허용 origin을 와일드카드로 설정하지 않습니다.
- 임의 웹사이트가 localhost로 보내는 요청으로 mode나 live_send_enabled를 바꿀 수 없어야 합니다.
- 브라우저에서 받은 chat_id를 검증 없이 전송 대상으로 사용하지 않습니다.
- 설정 변경은 검증·버전 갱신·감사 기록을 거칩니다.
- 대화·메모리·문서에 포함된 가짜 지침은 시스템 지침으로 재해석하지 않습니다.
- 사용자 입력을 SQL, shell, 코드로 실행하지 않습니다.
- 원격 접근 기능과 공개 서버 배포는 초기 기본 범위에 포함하지 않습니다.

## 14. 관측성과 검증 단계

### 단계 A: 결정적 시뮬레이터

합성 데이터와 mock transport로 상태 전이, 정책, 취소, 중복 방지, 실패 처리를 확인합니다.

권장 측정값:

- 이벤트 중복 관측 수와 중복 작업 생성 수
- stale 결과 폐기 수
- 사용자 개입 후 취소 수
- 정책상 보류 이유별 수
- 전송 시도 횟수와 불명확 결과 수
- 생성·dispatcher 대기·로컬 확인 지연

실행 전에는 모든 측정값을 미측정으로 기록합니다. 코드 줄 수나 테스트 개수로 신뢰성을 대신 설명하지 않습니다.

### 단계 B: Mac 읽기 검증

실제 Mac, 설치한 kmsg 버전, 카카오톡 버전에서 다음을 확인합니다.

- 손쉬운 사용 권한과 로그인 상태
- 대상 채팅방 바인딩
- 본인·상대·시스템 메시지 식별
- 휴대폰에서 보낸 본인 메시지 관측
- 창 전환·일시적 읽기 실패·재시작 후 상태

이 단계만으로 실제 전송 검증이 끝났다고 보고하지 않습니다.

### 단계 C: 범위가 정해진 실제 전송 검증

사용자가 명시한 테스트 대상과 내용·범위에서만 수행합니다. 코드 작성과 mock 테스트 권한을 실제 개인 메시지 발송 권한으로 해석하지 않습니다.

최종 보고에는 각 실행 환경, 버전, 실행한 항목, 결과, 남은 한계를 구분합니다. 단일 성공 사례로 장시간 무인 운용을 보장하지 않습니다.

## 15. 장애 시 기본 행동

| 장애 | 기본 행동 |
|---|---|
| Keychain 잠금·키 접근 불가 | 민감정보 처리와 자동 전송 중지 |
| 카카오톡 로그인·권한·창 접근 문제 | 자동 전송 보류, 로컬 상태 표시 |
| 작성자·채팅방 식별 불명확 | 관련 자동 작업 보류 |
| 모델 네트워크 오류 | 제한된 생성 재시도 후 실패 기록 |
| LLM 출력 계약 위반 | 전송하지 않음 |
| 관측 공백·절전 복귀 | 기준 대화와 신선도 재검증 |
| DISPATCHING 이후 결과 불명확 | DELIVERY_UNKNOWN, 자동 재시도 없음 |
| 사용자의 즉시 중지 | 아직 시작하지 않은 전송 차단, 진행 작업 취소 |

이미 UI에 제출된 메시지를 중지 버튼으로 회수할 수 있다고 표시하지 않습니다.
