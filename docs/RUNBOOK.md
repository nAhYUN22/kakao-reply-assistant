# 개발 실행과 후속 실기기 검증

## 1. 합성 앱 실행

저장소 루트에서 `make install` → `make build` → `make serve`를 실행하고 http://127.0.0.1:8765 를 엽니다. `make install`은 `uv sync --locked`와 `npm --prefix frontend ci`를 사용합니다. 설치된 `.venv`를 쓰며 실행기는 하나만 켜세요. Uvicorn reload와 여러 worker를 사용하지 않습니다.

- 기본 모의/off 상태에서 모의 자동 또는 초안을 선택합니다.
- 상대 합성 메시지를 입력하고 +600초를 진행합니다. +599초에서는 생성되지 않습니다.
- 이력에서 모의 발송 확인 또는 초안 상태와 상세 본문을 확인합니다.
- 다음 상대 입력 후 본인 답장을 입력하면 취소 이력이 남습니다. 즉시 중지하면 mode=off가 됩니다.
- `make test`는 Python과 UI 테스트, `make smoke`는 격리된 임시 DB의 API 수직 시나리오입니다.
- UI 개발은 별도 터미널에서 `make dev-ui`; http://127.0.0.1:5173 의 /api 프록시를 사용합니다.

DB 기본 경로는 `data/mock.sqlite`이며 `KAKAOREPLY_DB_PATH`로 합성 전용 다른 경로를 지정할 수 있습니다. 일반 서버 실행은 `--no-access-log`로 요청 경로 로그를 끕니다. 기본 metadata-only 모드에서는 원문·생성문을 DB에 쓰지 않고 재시작 시 사라집니다. 아래 Keychain 설정을 선택하면 생성문을 암호화 저장합니다. 작업 메타데이터와 발송 시도는 남고 미완료 작업은 복구 정책에 따라 취소 또는 전송 불명으로 바뀝니다. 재시작 후 자동 모드는 항상 꺼져 있습니다.

앱은 가짜 시계를 수동 전진하는 합성 도구입니다. M2의 7일 본문 만료도 이 시계로 검증하며, 실시간 보존 작업·실계정 연결 복구를 검증했다고 해석하지 마세요. 실행 중지에는 터미널 Ctrl+C를 사용합니다. 테스트 데이터 초기화가 필요하면 먼저 서버를 종료하고 기존 DB를 다른 위치에 보관한 뒤 새로운 `KAKAOREPLY_DB_PATH`로 시작하세요. 불명 이력 제거는 실제 발송 복구 절차가 아닙니다.

### M2 저장소와 생성문 삭제

`make smoke-m2`는 임시 합성 키/DB와 가짜 MCP 서버만 사용합니다. 실제 Keychain/카카오톡에 접근하지 않습니다.

화면의 생성문 상세 → 로컬 생성문 삭제 → 확인하고 삭제 순서로 본문을 지웁니다. 이미 발송한 메시지를 회수하지 않습니다. 아직 생성 중인 작업은 취소하며 발송 진행 중에는 삭제를 거부합니다. 중복 방지용 작업·시도 메타데이터는 유지합니다.

macOS Keychain 저장을 선택할 때만 아래 명령을 사용합니다. 이번 개발에서는 이 명령을 실행하지 않았습니다. 서버를 중지하고 DB를 백업한 다음 선택하세요. 암호화 활성화 후에는 같은 키가 있어야 다시 열리며, 키 누락·잠금·교체 시 평문이나 임시 키로 우회하지 않습니다.

```bash
PYTHONPATH=backend .venv/bin/python -m kakaoreply.storage_setup init-key --key-id kakaoreply-v1
KAKAOREPLY_KEY_STORE=keychain KAKAOREPLY_KEY_ID=kakaoreply-v1 make serve
```

키 값 자체는 환경변수·로그·설정 파일에 넣지 않습니다. 설정은 키 참조만 받습니다. 기존 정상 키는 재생성하지 않습니다. 이 설정을 해도 transport는 mock입니다.

생성문은 암호화 저장 후 발송하며 저장 실패 시 off로 전환합니다. 기본 7일 경과 후 시작/가상 시간 진행/상세 조회 시 만료 본문을 제거합니다. 메모리 모의 전송기 복사본도 삭제/만료 시 정리합니다. SQLite 잔여 암호문이나 OS 백업까지 완전 삭제하는 기능은 아닙니다. 감사 메타데이터의 30일 정리는 중복 방지 tombstone 설계와 함께 후속 구현합니다.

이 Mac에는 Homebrew로 kmsg 1.260921.0을 설치했습니다. 설치본 초기화·도구 목록·읽기 스키마를 확인했습니다. 실제 대화 읽기는 아래 로컬 화면에서 실행합니다.

## 2. Mac 연결 진단

작성자 안내 기준 kmsg 설치 경로는 Homebrew입니다. 설치 버전의 도움말과 공식 저장소를 다시 확인합니다.

```bash
brew install channprj/tap/kmsg
kmsg --version
kmsg --help
kmsg status
```

`status`는 손쉬운 사용 권한·앱 실행·인증 상태를 점검할 수 있으므로, 실행하는 사용자 세션에서 안내를 확인해야 합니다. 이번 확인 결과 손쉬운 사용 권한은 미허용이었습니다. 시스템 설정 → 개인정보 보호 및 보안 → 손쉬운 사용에서 실행 파일을 추가해 켜세요. 이 Mac에서는 파일 선택 창에서 ⌘⇧G를 누르고 /opt/homebrew/bin/kmsg를 입력할 수 있습니다.

- Mac OS 버전, KakaoTalk 버전, kmsg 버전을 기록합니다.
- 손쉬운 사용 권한은 실제 사용하는 바이너리에 부여되어야 합니다.
- 카카오톡 계정 암호나 kmsg의 인증 저장 파일을 앱·Codex 대화로 복사하지 않습니다.
- 로그나 진단 결과에는 대화방 이름·본문·자격 증명을 제거합니다.

## 3. 실제 읽기 검증

[로컬 앱](http://127.0.0.1:8765)에서 **Mac 카카오톡 읽기 진단 → 진단 열기**를 선택합니다. Mac 카카오톡에 로그인하고 대상 1:1 대화창을 따로 열어 둡니다. **실제 대화 목록 조회**를 누르면 kmsg CLI에서 관측한 방 제목을 이 브라우저에 표시합니다. 목록 조회 과정에서 카카오톡 창 상태가 바뀔 수 있습니다. 대상 선택과 1:1 확인 후 **선택한 대화 읽기 확인**을 누릅니다. 목록과 대상을 다시 대조한 뒤 같은 MCP 연결에서 두 번 읽고 기준선 건수와 새로 관측한 건수를 표시합니다. 새 메시지가 없는 경우 두 번째 관측에서 변화 없음이 정상입니다. 결과가 모호하면 다시 목록을 확인하세요. 대화 원문·실명·스크린샷을 Git이나 Codex로 옮길 필요가 없습니다.

다음은 후속 작성자 식별과 운영 검증의 범위입니다.

1. 읽기 가능한 채팅방 목록을 확인하고 정확한 대상 이름을 선택합니다.
2. 앱의 binding과 upstream 식별자 성격을 확인합니다.
3. 같은 이름의 대화가 있으면 자동 발송을 켜지 않습니다.
4. 본인·상대·봇 echo를 구분할 수 있는 합성 테스트 대화를 준비합니다.
5. 휴대폰에서 직접 보낸 메시지가 Mac에서 관측되는지 확인합니다.
6. 창 상태가 바뀌거나 앱이 잠겼을 때의 결과를 기록합니다.
7. 관측 공백·작성자 불명을 정상 신규 메시지로 처리하지 않는지 확인합니다.

실제 내용을 코드 fixture로 저장하지 않습니다. 구조 확인이 필요하면 사람이 내용을 제거한 최소 예시를 사용합니다.

## 4. MCP 검증

- `kmsg mcp-server`를 앱의 stdio 클라이언트에서 시작합니다.
- 초기화, `tools/list`, 허용된 읽기 호출, 결과 파싱, 종료를 검증합니다.
- 로그는 stderr로 분리하고 프로토콜 stdout을 오염시키지 않습니다.
- 실제 도구 이름·입력 스키마·`confirm` 의미를 기록합니다.
- CLI 호출 테스트만 했으면 'CLI 검증'이라고 적습니다.
- 지원하지 않는 도구·스키마를 만나면 실제 발송을 보류하고 호환성 오류로 표시합니다.

## 5. 초안과 실제 전송 검증

### 초안

- 실제 읽기를 사용하더라도 전송 호출은 0회여야 합니다.
- `--dry-run` 결과는 전송 계획 확인이며 카카오톡 전송 성공을 증명하지 않습니다.
- MCP의 확인 관련 플래그를 이름만 보고 설정하지 않습니다.

### 실제 전송

실제 테스트 대상·내용·횟수가 승인된 경우에만 진행합니다. 사용자가 이후 앱에서 대상과 정책을 설정해 자동 모드를 켜면 그 동일 범위의 정상 응답마다 확인을 반복하지 않습니다.

1. 자동 응답 표시를 포함한 최종 본문을 확인합니다.
2. 선택한 대상과 현재 binding을 확인합니다.
3. 발송 의도 저장·최종 재조회·외부 호출·대응 outgoing 확인을 검증합니다.
4. 호출 성공만으로 상대 수신·읽음을 주장하지 않습니다.
5. 결과가 불명확하면 자동 재시도하지 않고 해당 binding을 보류합니다.

## 6. 장애 복구

| 현상 | 기본 처리 | 확인할 항목 |
|---|---|---|
| 대상 이름 변경 | 자동 응답 보류 | 새 binding과 운영자 재확인 |
| 작성자 불명 | 발송 보류 | 원본 구조·버전·파서 근거 |
| 모델 오류 | 제한된 생성 재시도 후 보류 | 공급자 상태·시간 초과·원문 없는 오류 코드 |
| 발송 시간 초과 | DELIVERY_UNKNOWN | Mac 대화창의 대응 outgoing, 자동 재전송 금지 |
| Mac 절전 복귀 | 기준선 재검사 | 관측 공백·후보 만료·직접 답장 여부 |
| Keychain 접근 실패 | 실데이터 처리 중지 | 키 접근 권한·키 존재, 평문 우회 금지 |
| 두 실행기 동시 시작 | 하나만 실행 | 프로세스 잠금과 DB 작업 소유권 |
| UI 연결 끊김 | 현재 상태 재조회 | SSE 재연결, 실제 엔진은 별도 상태 관리 |

전송 불명 reconciliation은 관측 증거를 기록하는 작업입니다. 이를 누르면 이전 메시지를 다시 보내는 숨은 동작이 있어서는 안 됩니다.

## 7. 중지와 제거

- 즉시 중지 후 아직 시작하지 않은 발송이 0회인지 확인합니다.
- 실행 중이던 외부 전송의 결과는 별도로 표시합니다.
- 자동 시작 등록은 사용자가 선택했을 때만 추가하고 제거 경로를 제공합니다.
- 앱 중지와 대화 데이터 삭제는 구분합니다.
- 보관기간 만료·선택 삭제 시 원문과 파생 자료·캐시를 함께 처리합니다.
- 개인 키 삭제로 데이터를 복호화할 수 없게 되는 영향을 사전에 설명합니다.
- 운영체제 백업까지 안전 삭제했다고 보장하지 않습니다.

## 8. 출시 전 증거

`PROGRESS.md`에 코드 구현, mock 검증, Mac 읽기, Mac 발송, 자동 모드 검증을 분리해 기록합니다. 불명 상태를 임의 성공으로 바꾸지 않습니다. 제품 테스트 전부와 문서 정합성 검사를 혼동하지 않습니다.
