## 1. 제품 목표와 범위

### 1.1 제품 정의

KakaoReply는 사용자의 Mac에서 실행되는 카카오톡 대리 답장 앱입니다. 사용자가 지정한 연인과의 1:1 대화에서, 설정한 작동 시간과 미응답 대기시간을 충족하면 최근 대화·확인된 기억·사용자가 입력한 현재 상태·본인 말투 예시를 참고해 답장을 생성하고 자동 발송합니다. 본인이 직접 답하면 준비 중인 자동 응답을 취소합니다.

사용자는 처음에 대상과 작동 범위를 정하고 자동 모드를 켭니다. 그 범위 안의 일상 답장을 매번 승인받는 흐름으로 바꾸지 않습니다. 자동 발송은 최종 제품의 필수 기능입니다. 개발·검증은 모의 연결부터 진행합니다.

### 1.2 성공 조건

- 선택한 대화에만 동작합니다.
- 사용자가 평소 쓸 법한 짧고 자연스러운 답장을 만듭니다.
- 사용자가 직접 답했거나 대화가 바뀌면 오래된 후보를 보내지 않습니다.
- 존재하지 않는 일정·위치·행동·약속을 만들어 답하지 않습니다.
- 전송 결과를 확신할 수 없을 때 중복 발송을 피하고 불확실성을 표시합니다.
- 사용자가 지금 어떤 범위에서 자동 응답 중인지 이해하고 즉시 멈출 수 있습니다.
- 자동 응답임을 상대가 알아볼 수 있도록 발송문에 표시합니다.

### 1.3 명확히 구분할 개념

| 개념 | 이 프로젝트의 의미 |
|---|---|
| 말투 학습 | 처음에는 본인이 확인한 예시와 말투 프로필을 프롬프트에 넣는 개인화입니다. 파인튜닝은 별도 후속 범위입니다. |
| 기억 | 출처·대상·유효시간이 있는 대화 정보입니다. 모델의 추측을 사실로 저장하지 않습니다. |
| 미응답 시간 | 프로그램이 측정하는 대기시간입니다. 상대의 서운함이나 관계 만족도를 보장하는 수치가 아닙니다. |
| MCP | 앱이 카카오톡 도구를 호출하는 연결 규약입니다. 자동 스케줄링·말투 학습·판단을 모두 대신하는 기능은 아닙니다. |
| Codex 개발 에이전트 | 코드를 작성·검토하는 도구입니다. 운영 중 연인의 메시지에 응답하는 LLM과 역할이 다릅니다. |
| 자동 발송 | 사용자가 켜둔 정책에 따라 앱의 결정적인 로직이 전송합니다. LLM이 자유롭게 카카오톡 도구를 실행하지 않습니다. |

### 1.4 v1 범위

- Mac 사용자 1명, 지정한 1:1 채팅방 1개
- 텍스트 메시지 수신·생성·전송
- `off`, `draft`, `auto` 모드
- 실제 MCP 연결과 독립적인 모의 연결
- 작동 시간대, 미응답 시간, 직접 답장 우선, 응답 한도
- 말투 예시 가져오기·편집·평가
- 최근 문맥, 출처가 있는 기억, 유효시간이 있는 현재 상태
- 로컬 설정 화면, 이력, 중지, 오류 복구
- 합성 데이터로 실행되는 전체 시뮬레이터

### 1.5 v1 제외 및 후속 범위

- 단체방·여러 연인/계정 관리·대량 발송
- 상대가 사람과 실시간으로 대화한다고 오인시키기 위한 숨김·가짜 타이핑·인위적 오타
- 사진·보이스톡·음성 메시지·스티커의 의미 분석
- 카카오톡 비공개 프로토콜 구현, 인증 우회, DB 복호화
- 약속 자동 확정, 구매·결제, 다른 계정에 대한 행동
- 관계의 감정 점수 또는 서운함 확률 산출
- 원격 공개 웹 서비스, 다중 사용자 SaaS, Kubernetes 배포
- 모델 파인튜닝, 독립 벡터 DB, 네이티브 앱 패키징

후속 기능은 v1 인수 기준을 충족한 뒤 별도 결정 기록으로 추가합니다.

## 2. 사용자 흐름

### 2.1 첫 실행

1. 모의 연결 화면이 열리고 실제 카카오톡에는 접근하지 않습니다.
2. 예시 대화로 타이머·직접 답장 취소·생성·전송 이력을 체험합니다.
3. 사용자가 실제 연결 설정으로 이동하면 Mac 환경과 `kmsg` 상태를 진단합니다.
4. 채팅방 목록에서 대상 1개를 선택하고 정확한 이름·1:1 여부·본인과 상대의 발신 구분을 확인합니다.
5. 말투 예시를 선택하거나 대화 내보내기 파일을 로컬에서 가져옵니다.
6. 모델 공급자, 대화 전송 대상, 작동 시간대와 응답 한도를 확인합니다.
7. 초안으로 생성 품질을 확인한 뒤, 사용자가 자동 모드를 활성화합니다.

한 번 설정된 범위 안의 자동 답장마다 확인 팝업을 요구하지 않습니다. 범위가 바뀌거나 대상 식별에 문제가 생기면 자동 모드를 보류합니다.

### 2.2 사용 중

- 상대 메시지를 감지하면 대기 중임을 표시합니다.
- 상대가 여러 메시지를 나누어 보내면 한 묶음으로 답합니다.
- 사용자가 직접 답하면 예약·생성 결과가 무효화됩니다.
- 답할 시점에 최근 대화를 다시 확인하고 후보를 생성합니다.
- 최종 전송 조건을 재확인한 뒤 한 번의 전송 시도를 합니다.
- 결과를 확인 가능한 수준으로 표시합니다. 상대가 읽었다고 추측하지 않습니다.
- 확인이 필요한 내용은 로컬 알림과 초안으로 넘깁니다.

### 2.3 대표 시나리오

| 상황 | 기대 동작 |
|---|---|
| 상대가 일상 근황을 보냈고 사용자는 회의 중입니다. | 확인된 회의 상태와 최근 문맥을 참고해 짧은 답장을 생성합니다. |
| 상대가 만나자는 시간을 제안했습니다. | 앱이 사용자를 대신해 새로운 약속을 확정하지 않고 사용자 확인으로 넘깁니다. |
| 사용자가 휴대폰에서 답했습니다. | 해당 발신이 관측되면 아직 제출되지 않은 자동 답장을 취소합니다. |
| 상대가 연속해서 세 문장을 보냈습니다. | 첫 미응답 시각을 유지하고 마지막 수신 뒤 묶음 대기시간을 둡니다. |
| Mac이 절전 상태였다가 돌아왔습니다. | 오래된 대화에 몰아서 답하지 않고 현재 상태부터 다시 확인합니다. |
| 발송 도구가 시간 초과했습니다. | 보내지지 않았다고 단정하지 않고 전송 불명으로 표시합니다. 자동 재발송하지 않습니다. |
| 상대가 `/봇중지`를 보냈습니다. | 알려진 대상에서 온 정확한 중지 명령이면 자동 응답을 멈추고 사용자에게 알립니다. |

## 3. 우선순위와 기본값

### 3.1 우선순위

- P0: 실제 사용 전에 필요한 기능입니다. 자동 전송, 본인 개입 처리, 대상 고정, 중복·불확실 전송 처리, 모의 실행, 기본 UI, 데이터 보호를 포함합니다.
- P1: 사용성·개인화 품질을 개선합니다. 예시 검색 개선, 통계, 더 나은 알림, 로그인 시 자동 시작 옵션 등입니다.
- P2: 충분한 평가 뒤 검토합니다. 파인튜닝, 네이티브 앱 배포, 다양한 첨부파일 처리 등입니다.

### 3.2 초기 설정

아래 숫자는 조절 가능한 설계 기본값입니다. 관계나 모델 성능에 대한 보장값이 아닙니다. 최종 소스는 `examples/app-config.example.json`입니다.

| 설정 키 | 초기값 | 단위·의미 |
|---|---:|---|
| `transport` | `mock` | 실제 연결은 `kmsg_mcp`, 선택적 대안은 `kmsg_cli` |
| `mode` | `off` | `off` / `draft` / `auto` |
| `live_send_enabled` | `false` | 실제 전송을 허용하는 운영 설정 |
| `active_windows` | `[]` | 실제 자동 모드 전에는 최소 1개 구간 설정 |
| `timezone` | `Asia/Seoul` | IANA 시간대 |
| `reply_delay` | 600 | 초, 첫 미응답 이후 대기 |
| `settle` | 20 | 초, 마지막 상대 메시지 이후 묶음 대기 |
| `human_cooldown` | 900 | 초, 직접 답장 후 본인 대화 우선 기간 |
| `poll` | 5 | 초, 초기 주기적 읽기 간격 |
| `max_incoming_age` | 1800 | 초, 이보다 오래된 미응답은 자동 처리하지 않음 |
| `max_autoreplies_session` | 3 | 연속 자동 응답 세션 한도 |
| `session_gap` | 1800 | 초, 대화 세션 구분에 사용하는 무활동 간격 |
| `max_per_hour` | 6 | 최근 60분의 자동 발송 시도 상한 |
| `max_per_day` | 20 | 설정 시간대 기준 하루의 자동 발송 시도 상한 |
| `max_chars` | 240 | 자동 응답 표시까지 포함한 최종 문자 수 |
| `llm_timeout` | 30 | 초, 생성 요청 제한 |
| `llm_retries` | 1 | 첫 호출 이후 추가 생성 재시도 수 |
| `disclosure_mode` | `per_message` | v1 고정 |
| `disclosure_suffix` | `— 부재중 AI 답장` | 전송 엔진이 붙이는 표시 |
| `storage.raw_retention_days` | 7 | 원문·일반 생성문의 보관 기간 |
| `storage.audit_retention_days` | 30 | 원문 없는 운영 메타데이터 보관 기간 |

실제 발송 시도에 들어간 작업은 결과가 불명확해도 한도에 포함합니다. 앱 재시작이나 모드 토글로 시간당·일일 한도를 초기화하지 않습니다.

## 4. 기능별 요구사항

### 4.1 연결과 대상

**FR-001 · P0 · 모의 실행**

- Mac·카카오톡·API 키 없이 합성 데이터로 전체 흐름을 실행할 수 있어야 합니다.
- 모의 모드의 화면에는 실제 발송이 아니라는 표시를 유지합니다.
- 모의 모드에서 실제 전송 어댑터가 호출되면 테스트 실패입니다.

**FR-002 · P0 · 실제 MCP 연결**

- `kmsg mcp-server` 프로세스와 연결해 초기화·도구 목록 조회·호출·종료를 구현합니다.
- 설치된 버전의 도구 스키마를 확인하고 버전·도구 목록의 증거를 남깁니다.
- CLI만 실행한 결과를 MCP 연결 완료로 보고하지 않습니다.
- 도구 이름이나 매개변수를 기억에 의존해 고정하지 않습니다.

**FR-003 · P0 · 대상 바인딩**

- 앱 내부 `binding_id`, 확인한 카카오톡 표시 이름, `kmsg` 로컬 식별자, 확인 시각과 연결 버전을 보관합니다.
- 사용자 선택 범위는 1:1 채팅방 1개입니다.
- 이름 중복·변경·식별 불명은 자동 발송 보류 사유입니다. 비슷한 이름의 방으로 대체하지 않습니다.
- 대상 변경은 기존 작업을 취소하고 새 바인딩 확인을 요구합니다.

**FR-004 · P0 · 발신자와 발생 순서**

- 본인·상대·시스템·불명 발신자를 구분합니다.
- 본인 발신 중 직접 작성과 앱의 자동 발신을 별도로 추적합니다.
- 같은 사람이 같은 분에 같은 문장을 두 번 보낸 경우 두 개의 발생으로 보존합니다.
- UI에서 식별을 확신하지 못하는 경우 본인이라고 가정하지 않습니다.

**FR-005 · P0 · 최초 실행 및 재연결**

- 최초로 관측한 대화는 기준선으로만 사용하고 자동 답장하지 않습니다.
- 절전·재시작·연결 끊김 뒤에는 새 기준선과 기존 작업을 재검사합니다.
- 관측 공백 중의 대화는 자동으로 신규 수신으로 몰아서 처리하지 않습니다.

### 4.2 모드와 시간 정책

**FR-010 · P0 · 모드**

- `off`: 예약·생성·발송을 실행하지 않습니다. 사용자가 연결 진단을 요청하면 그 범위의 진단만 수행합니다.
- `draft`: 입력과 정책을 처리해 초안을 보여주되 실제 전송 호출은 0회입니다.
- `auto`: 사용자가 켠 범위 안에서 발송 조건을 충족하는 답장을 자동으로 보냅니다.
- `mock` 연결에서는 같은 모드를 시뮬레이션할 수 있지만 실제 카카오톡에 접근하지 않습니다.

**FR-011 · P0 · 자동 모드 시작**

- 실제 대상 확인, 공급자 설정, 작동 시간대, 응답 한도, 자동 답장 표시가 준비되어야 합니다.
- 운영자가 자동 모드를 켠 이후 동일 범위의 일상 답장마다 승인을 반복하지 않습니다.
- 수신 메시지·LLM 출력·프로필 파일이 `live_send_enabled`나 대상을 바꿀 수 없습니다.

**FR-012 · P0 · 지연 및 묶음 처리**

- 첫 미응답 시각과 마지막 상대 메시지 시각을 분리합니다.
- 5장의 시간식을 구현하고 가짜 시계로 검증합니다.
- 입력이 계속 이어지는 동안 오래된 문맥으로 답하지 않습니다.
- 대기 중 메시지가 만료되면 강제로 보내지 않고 보류합니다.

**FR-013 · P0 · 본인 개입 우선**

- 타이머 대기, 생성 중, 전송 준비 단계 모두에서 직접 발신이 관측되면 취소합니다.
- 생성 요청 취소가 불가능해도 늦게 도착한 결과를 폐기합니다.
- 발송 직전 새 스냅샷을 읽어 이전 결정의 유효성을 검사합니다.
- 원격 UI 전송과 휴대폰 발신 사이의 경쟁을 완전히 없앴다고 보장하지 않습니다.

**FR-014 · P0 · 중지와 한도**

- 즉시 중지는 아직 외부에 제출되지 않은 작업을 차단합니다.
- 이미 시작한 발송을 되돌렸다고 표시하지 않습니다.
- 세션·시간당·일일 한도를 보관하고 자동 폭주를 막습니다.
- 대상에게 안내한 `/봇중지` 요청은 허용된 정지 기능만 수행합니다. 재활성화는 로컬 사용자 UI에서만 합니다.

### 4.3 말투와 대화 기억

**FR-020 · P0 · 말투 자료 가져오기**

- 사용자가 선택한 대화 내보내기 텍스트 또는 직접 붙여 넣은 예시를 처리합니다.
- 지원하는 파일 형식과 인코딩을 명시하고, 파일 안에서 본인 표시명을 사용자가 선택하게 합니다.
- 원본 전체가 모델로 즉시 전송되지 않도록 파싱·선택·미리보기 단계를 둡니다.
- 읽지 못한 행·날짜·발신자를 숨기지 말고 제외 이유와 개수를 표시합니다.
- 경로 탐색·명령 실행·외부 URL 접근은 수행하지 않습니다.

**FR-021 · P0 · 인간 작성 예시만 사용**

- 본인이 직접 작성했다고 확인한 메시지와 명시적으로 채택한 수정본만 스타일 예시로 사용합니다.
- 자동 발송문, 작성자 불명, 인용·전달문, 상대 문장은 제외합니다.
- 오래된 가져오기 자료에서 인간 작성 여부가 불명확하면 사용자가 고른 예시만 채택합니다.
- 앱 출력이 다시 학습 자료로 순환해 말투를 바꾸지 않게 출처를 유지합니다.

**FR-022 · P0 · 말투 프로필**

- 호칭, 존댓말/반말 선호, 문장 길이, 문장 수, 이모티콘, 자주 쓰는 표현, 사용하지 않을 표현을 편집할 수 있어야 합니다.
- 프로필에는 버전과 근거 예시 식별자가 있어야 합니다.
- 말투 프로필에 현재 위치·일정·관계 판단·전송 권한을 저장하지 않습니다.
- 초기에 예시 기반 프롬프팅을 구현합니다. 파인튜닝을 필수 의존성으로 두지 않습니다.

**FR-023 · P0 · 대화 문맥**

- 최근 텍스트와 필요한 요약·확인된 기억을 모델의 입력 한도 안에서 조합합니다.
- 실제로 읽지 못한 과거 대화를 기억하는 것처럼 답하지 않습니다.
- 모델 입력 예산을 넘으면 최근 메시지와 관련 사실을 우선하고 제외한 범위를 기록합니다.
- 요약은 원문 이벤트를 참조하며, 원문의 수정·삭제·만료에 맞춰 무효화합니다.

**FR-024 · P0 · 사실 메모리**

- 각 기억에 내용, 대상, 출처 이벤트, 확인 상태, 유효 시작·만료, 수정 이력을 둡니다.
- 모델이 추출한 정보는 후보로 저장합니다. 사용자가 확정하기 전 본인의 새 일정이나 약속을 확정 사실로 사용하지 않습니다.
- 상대가 직접 전한 근황은 '상대가 그렇게 말함'이라는 출처를 보존해 최근 대화의 맥락으로 사용할 수 있습니다.
- 출처끼리 충돌하면 임의로 하나를 진실로 선택하지 않고 해당 사실을 답변 근거에서 제외하거나 확인 요청합니다.
- 정정·철회·삭제가 파생 요약과 검색 결과에도 반영되어야 합니다.

**FR-025 · P0 · 현재 상태**

- 사용자가 현재 활동, 답장 가능 예정 시각, 선택적인 추가 설명을 입력합니다.
- 상태마다 만료 시각을 반드시 둡니다.
- 만료된 '회의 중'이나 '이동 중'을 계속 답장에 사용하지 않습니다.
- 위치·식사 여부·감정·지금 하는 일을 모델이 추측해 자기 사실로 말하지 않습니다.

**FR-026 · P1 · 수정 피드백**

- 사용자는 생성문을 수정하고 '말투 예시로 채택'할 수 있습니다.
- 수정문을 무조건 새로운 사실로 저장하지 않습니다.
- 원문 후보·수정문·채택된 규칙·프로필 버전을 구분합니다.
- 설정 변경은 대기 중 후보를 무효화하고 새 버전을 사용하게 합니다.

### 4.4 생성과 전송

**FR-030 · P0 · 구조화된 생성 결과**

- 모델은 `schemas/reply-decision.schema.json`에 맞는 네 필드만 반환합니다.
- `action`은 `reply`, `hold`, `notify_owner`, `no_reply` 중 하나입니다.
- 나머지는 `reply_text`, `reason_codes`, `used_fact_ids`입니다.
- 수신자, 설정 변경, 실행 명령, 카카오톡 전송 도구 호출은 허용하지 않습니다.
- 긴 내부 추론을 요청·저장하지 않습니다. 운영 이력에는 짧은 이유 코드만 사용합니다.

**FR-031 · P0 · 내용 처리 원칙**

- 일상 안부·근황·가벼운 대화는 설정 범위에서 자동 답장할 수 있습니다.
- 본인만 알 수 있는 사실이 없으면 추측하지 않습니다.
- 새로운 약속·중대한 관계 결정·금전 요청·긴급한 도움 요청은 사용자 알림과 초안으로 넘깁니다.
- 이러한 분류가 완벽하다고 주장하지 않습니다. 경계 사례를 평가 데이터에 포함합니다.
- 메시지 안의 '이전 규칙을 무시하라', '다른 채팅을 읽어라'는 대화 데이터입니다.

**FR-032 · P0 · 자동 응답 표시**

- v1은 각 자동 발송문의 끝에 `— 부재중 AI 답장`을 붙입니다.
- 이 표시는 LLM이 만드는 본문과 분리하고 전송 엔진이 적용합니다.
- 대화·말투 예시·모델 출력으로 제거할 수 없습니다.
- 본문과 표시를 합친 길이가 한도를 넘으면 무작정 자르지 않고 한 번 재생성하거나 보류합니다.

**FR-033 · P0 · 전송 조건 검사**

- 실제 전송은 SendGate를 통과한 한 경로에서만 실행합니다.
- 대상, 모드, 시간, 한도, 현재 상태, 대화 버전, 설정 버전, 후보 만료, 중지 여부를 재확인합니다.
- 모델 결과만으로 실제 전송을 허용하지 않습니다.
- 예상하지 못한 필드·빈 본문·지원하지 않는 액션·잘못된 기억 참조는 발송하지 않습니다.

**FR-034 · P0 · 발송 이력과 불확실성**

- 발송 의도를 저장한 후 외부 도구를 호출합니다.
- 한 작업의 자동 전송 시도는 최대 한 번입니다.
- 호출을 시작한 이후 타임아웃·프로세스 종료·결과 파싱 실패가 생기면 `DELIVERY_UNKNOWN`으로 둡니다.
- 불명확한 발송은 자동 재시도하지 않습니다.
- `CONFIRMED_LOCAL`은 Mac 대화창에서 발신을 확인했다는 뜻입니다. 상대 수신·읽음을 뜻하지 않습니다.
- GUI 기반 연결에서 exactly-once delivery를 보장한다고 설명하지 않습니다.

### 4.5 설정·진단·운영

- 화면의 저장 성공은 실제 저장 성공 후 표시합니다.

**FR-041 · P0 · 이력**

- 후보 생성, 취소, 보류, 발송 시도, 로컬 확인, 전송 불명을 구분합니다.
- 모델·프롬프트·말투 프로필 버전과 사용한 기억 식별자를 확인할 수 있습니다.
- 일반 로그는 원문·API 키·연인 이름을 포함하지 않습니다.

**FR-042 · P0 · 비밀정보와 로컬 접근**

- 공급자 키와 앱 암호화 키는 Mac Keychain에 보관합니다.
- 키체인 실패 시 평문 파일에 저장하는 우회 경로를 두지 않습니다.
- 로컬 웹 서버는 루프백에 바인딩하고, 인증·Origin/Host 검사·CSRF 방어를 적용합니다.
- 외부 페이지가 로컬 설정 변경이나 발송 API를 호출할 수 없어야 합니다.

**FR-043 · P0 · 삭제와 보관**

- 원문 보관기간, 파생 기억, 예시, 이력의 보관을 구분합니다.
- 삭제된 원문을 근거로 한 요약·검색 결과·스타일 예시도 추적해 정리합니다.
- 사용자가 따로 보존하기로 선택한 예시는 일반 원문 만료와 구분해 표시합니다.
- SSD·운영체제 백업까지 안전하게 완전 삭제했다고 보장하지 않습니다.

**FR-044 · P1 · 자동 시작**

- 사용자가 선택한 경우에만 로그인 후 앱을 시작하는 옵션을 제공합니다.
- 자동 시작과 자동 발송 재활성화는 별도 설정입니다.
- 시작 직후에는 연결·기준선·남은 작업을 검증하고 오래된 메시지에 답하지 않습니다.

## 5. 응답 시간 정책

### 5.1 기준 시각

- `first_unanswered_at`: 현재 미응답 묶음의 첫 상대 메시지를 안전하게 관측한 시각
- `last_partner_at`: 같은 묶음의 마지막 상대 메시지 시각
- `human_cooldown_until`: 마지막으로 확인한 본인 직접 답장 이후 우선 기간 종료 시각

```text
due_at = max(
  first_unanswered_at + reply_delay,
  last_partner_at + settle,
  human_cooldown_until
)
```

상대 메시지가 추가되어도 최초 미응답 시각을 계속 뒤로 미루지 않습니다. 상대가 계속 입력 중이면 마지막 수신 후 `settle`을 기다립니다. 첫 미응답이 `max_incoming_age`보다 오래되면 해당 작업을 보류합니다.

### 5.2 시간 구간

- 저장 시각은 UTC, UI와 정책 평가는 선택한 IANA 시간대입니다.
- 구간은 시작 포함·끝 미포함으로 정의합니다.
- `22:00~02:00`은 시작일의 요일에 귀속하는 자정 넘김 구간입니다.
- 겹치는 구간은 합집합으로 취급해 작업을 복제하지 않습니다.
- 작동 시간대 밖의 메시지를 다음 구간에 몰아서 발송하지 않습니다.
- DST 시간대는 명시적으로 검증한 경우만 지원하며, 미지원이면 설정 단계에서 거절합니다.
- 실행 중 경과 시간은 단조 시계를 사용하고, 절전·시계 변경 뒤에는 정책을 재평가합니다.

### 5.3 직접 답장과 세션

- 직접 답장은 현재 미응답 묶음을 해결 처리하고 후보를 취소합니다.
- 이후 새 상대 메시지는 새 묶음이며, 본인 우선 기간이 끝나기 전에는 자동 전송하지 않습니다.
- 봇 발신은 본인 직접 답장으로 처리하지 않습니다.
- 봇 답장이 `CONFIRMED_LOCAL`로 확인되면 후보가 포함한 상대 입력 범위만 해결 처리하고 최초 미응답 시각을 비웁니다. 그 이후 새 상대 메시지는 새 묶음의 지연시간을 기다립니다. 봇 발신으로 본인 우선 기간이나 응답 한도를 초기화하지 않습니다.
- 한도 카운터는 실제 전송 시도 기준입니다. 불명확 발송도 포함합니다.
- 시간당·일일 한도는 앱 재시작, 모드 토글, 세션 재개로 초기화하지 않습니다.
- 세션 한도에 걸린 경우 UI에 이유를 표시합니다. 대화 무활동 후 새 세션을 만들더라도 미해결 전송 불명과 중지 상태는 유지합니다.

## 7. 데이터와 개인정보

- 대화·생성문·기억·채팅방명 등 민감한 데이터는 SQLite에 쓰기 전에 앱 계층에서 인증된 암호화로 보호합니다.
- 암호화 키는 Keychain에 보관합니다. '로컬 SQLite'라는 이유만으로 암호화됐다고 설명하지 않습니다.
- 평문 검색 인덱스나 임베딩 캐시에 원문이 남지 않도록 v1은 제한된 자료를 메모리에서 검색합니다.
- 외부 LLM은 사용자가 공급자를 선택했을 때만 사용합니다. 원문이 어느 서버로 전달되는지 설정 화면에 표시합니다.
- 로컬 모델 실패 시 다른 외부 공급자로 자동 전환하지 않습니다.
- `kmsg` 자체가 관리하는 인증정보는 앱의 키체인 관리 범위와 별개입니다. 앱이 해당 인증정보를 복제하거나 로그로 내보내지 않습니다.
- 개발 fixture, 저장소, Codex 프롬프트에는 실제 연인 대화나 API 키를 포함하지 않습니다.

### 8.1 기능 완료

- FR-001~005, 010~014, 020~025, 030~034, 040~043의 P0 동작이 구현됩니다.
- 모의 연결의 자동 응답 E2E가 실행됩니다.
- 실제 MCP transport 코드와 계약 테스트가 있으며, Mac 미검증 항목은 명확히 표시됩니다.
- `docs/TEST_PLAN.md`의 필수 인수 사례를 실행하고 결과를 기록합니다.
- `docs/RELIABILITY.md`의 발송 불변조건을 유지합니다.

### 8.2 말투 품질

- 프로필 작성용 자료와 보류 평가용 자료를 구분합니다.
- 평가 대상의 실제 답장을 생성 입력 예시로 넣지 않습니다.
- 자연스러움, 본인 말투 유사도, 맥락 적합성, 사실 오류, 답장 길이를 별도로 평가합니다.
- 평균 점수가 높아도 허위 사실·대상 오류·취소 실패는 별도의 실패입니다.
- 자동 평가 점수만으로 본인 말투를 완벽히 재현했다고 결론 내리지 않습니다.

## 9. 개발 순서와 역할

1. 계약·스키마·모의 연결·가짜 시계·상태 기계를 먼저 구현합니다.
2. 설정 화면과 시뮬레이터를 연결합니다.
3. 실제 MCP 읽기와 대상/발신자 판별을 검증합니다.
4. 말투·기억·구조화된 생성과 평가를 연결합니다.
5. SendGate·outbox·제한된 자동 전송을 구현합니다.
6. 장애 복구·로컬 접근 보호·데이터 삭제를 검증합니다.

두 사람이 작업할 때 한 명은 연결·엔진·DB·발송을, 다른 한 명은 UI·말투 편집·평가 화면·E2E를 맡는 구성이 적당합니다. API와 이벤트 계약은 먼저 합의합니다. Codex의 병렬 에이전트도 같은 파일을 동시에 수정하지 않도록 책임을 나눕니다.
